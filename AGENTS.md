# Agent instructions

My machines in one public repo: a folder per tool in `loadouts/` (its manifests, its scripts in `.loadout/`, its dotfiles in `home/` for `$HOME` and `root/` for `/`; chezmoi reads `.chezmoi-home/`, built from them) and the TypeScript manifests (`loadout.ts` and the `*.loadout.ts` it includes, typed by the SDK's types loadout writes into `node_modules/@types/loadout`) that `loadout repo compile` turns into `loadout.lock.json`, the only thing loadout reads.

## Every change

- Run `git commit` or `git push` only when the user explicitly asks in that turn, never from “go” or a finished task. Commits follow the existing style (short lowercase imperative, why over what); a push pushes the current branch.
- This repo and its history are public: nothing names the employer, its clients, their tools or private repos, nor a work machine or its hostname, and no secret comes in (a token comes from 1Password, `onepasswordRead`). The work laptop is a private child repo's machine; before renaming anything or adding what only it needs, read `docs/child-repo.md`.
- After editing any manifest (`loadout.ts`, `*.loadout.ts`, `machines/`), run `loadout --repo <checkout> repo compile` and commit the lock (`.chezmoi-home/` and `.chezmoi-root/`, chezmoi's sources built from the tool folders with the templates' data, are ignored: every loadout command rewrites them; never edit them), and type-check (`bun install` once, then `loadout bun node_modules/typescript/bin/tsc --noEmit -p .`; the pre-commit hook does, on every commit of a `.ts` file). Keep its warnings clean: use what it calls unused, delete it, or say why it stays with `keepUnused: "…"`.
- chezmoi doesn't delete a target whose source is gone: when a removed file should also leave the machines, add its destination path to its tool's `home/.chezmoiremove`.
- Before writing a new script, look for one that already does the job, or nearly (`git grep` the setting, file or command; read the neighbours in its `.loadout/` and the shared helpers: `lib/` and the tools' `.loadout/lib/`, each imported by a `#` name that `docs/layout.md` lists). Reuse it, or extend it when it falls a little short, rather than adding a near copy: Hyprland settings, binds and unbinds go in `loadouts/hypr/.loadout/hypr-config/<file>.lua` (`omarchy-hypr-config`), not in a script of their own.
- Templates branch on machine data, never on `.chezmoi.hostname`: `{{ if (includeTemplate "loadout/machine" . | fromJson).omarchy }}`. A new setting is a key in the data schema (`machines/data.ts`) first. `.chezmoi.os` stays: the OS is a fact, not a setting.
- `machine new` runs in two phases, core then later (each: programs, then scripts). **Core is a working machine with a functional zsh**: zsh as the login shell and its plugins, tmux with tpack and its plugins, Neovim and its plugins, the shell's CLI tools (starship, atuin, fzf, zoxide, eza, bat), mise with the default version of `node`, `python`, `neovim` and `go` (`miseTools({ tools: […] })`), git, ssh and the GitHub key, 1Password, the hardware fixes, and every step that asks the user something (sudo, a passphrase, a browser login, 1Password's approval), so the slow part needs nobody. `canWait: "why"` is for what's slow and not needed to work: big app downloads, large Homebrew installs, VMs, SDKs, the other mise versions (`mise-tools-later`), builds from source. A new or changed program or script is core unless it's clearly that; when unsure, ask. Compile refuses a core step that depends on or runs after a later one: never fix that by marking a core item later, and if a later item turns out to be needed for the core, drop its `canWait`. A core script runs before every later program, so a script that cleans up after what installs leave behind (not one program: `unlink-brew-glib` after brew's glib) is later and names what it follows in `runAfter`; "programs before scripts" only holds within a phase. Check where a change lands with `loadout --repo <worktree> machine new --dry-run` (later steps print under "Later, after everything above:"), and keep the shell working before the later phase: nothing zsh loads at startup may fail without a later item (guard it, as `plugins/java` and `plugins/android` do).

## In a feature worktree

`LOADOUT_REPO` and `chezmoi source-path` both point at the main checkout, so pass `--repo <worktree>` to every loadout command and `--source "$(git rev-parse --show-toplevel)"` to every chezmoi command. Never apply a whole worktree. Trying, finishing and abandoning a feature: `docs/worktrees.md`.
