# Agent instructions

## Git

Only run `git commit` or `git push` when the user explicitly asks to commit or push. Do not infer that from nearby work, “go”, or finishing a task.

If they ask to commit, follow their existing commit style (short lowercase imperative, why over what). If they ask to push, push the current branch. Do neither unless named in that turn.

## Layout

One repo for loadout and chezmoi. `loadout.toml` is loadout's root file (`[layout]` says where everything lives; `[data]` declares every per-machine setting with its default), `machines/<hostname>.toml` sets this machine's values, and `state/` is loadout's generated state. chezmoi reads only `configs/` (`.chezmoiroot`): its special files (`.chezmoiignore`, `.chezmoiremove`, `.chezmoitemplates/`) live there, and nothing at the repo root is deployed. Dotfiles move into `configs/` one slice at a time; until a tool's slice, its files sit at their old place, where chezmoi doesn't read them.

Everything loadout knows about a tool that has a config sits beside that config: `.loadout.toml` (its `[programs.*]`, `[scripts.*]`, `[outdated.*]`) and `.loadout/` (their scripts), e.g. `configs/private_dot_config/zsh/`. chezmoi never deploys dot entries that aren't its own special files, so neither reaches `$HOME`. Paths in a fragment are relative to it, and its commands run in its directory with `LOADOUT_REPO` set; shared helpers live in `maintenance/lib/` (`"$LOADOUT_REPO/maintenance/lib/…"`). A tool whose config is a single file in a folder other tools share (e.g. `configs/private_dot_config/starship.toml`) keeps its fragment in `programs/<tool>.toml` instead, since a `.loadout.toml` there would belong to no one tool. Config-less programs live in `programs/` and config-less scripts in `maintenance/<concern>/`, a folder per concern holding its fragment and scripts together (e.g. `programs/brew/`: the `brew`/`brew-cask` installers, `setup-brew`, `brew-taps`). An install mechanism beyond loadout's built-ins lives with its concern; anything elsewhere that needs brew by a custom command calls `sh "$LOADOUT_REPO/programs/brew/brew.sh" …`.

Machine and profile files are grouped by tool or concern, like the repo: one table per group with its `install` (the variant for the program named like the group, or `[<group>.install]` for several), its `scripts` opt-ins and its `[<group>.data]` (= `[data.<group>]`), plus machine-wide `[data]`. `profiles/<name>.toml` hold what machines of a kind share, one subject each (e.g. `profiles/omarchy.toml`); `machines/<hostname>.toml` are real hosts and `extends = [...]` a list of profiles. A machine overrides its profiles; two profiles of one list disagreeing is a loadout error.

Templates branch on machine data, never on `.chezmoi.hostname`: `{{ if (includeTemplate "machine" . | fromJson).omarchy }}`. The `machine` partial merges `loadout.toml`'s `[data]`, then the machine file with its profiles beneath (`machine-layer`, recursive over `extends`; groups' `[<group>.data]` included; `merge-data`: tables key by key, everything else replaces, as loadout merges); a host without a machine file gets the defaults. A new setting is declared in `loadout.toml [data]` first: loadout refuses a machine file setting an undeclared key. OS checks (`.chezmoi.os`) stay: the OS is a fact, not a setting.

## Chezmoi

Chezmoi does not delete destination files just because they left the source. Whenever a file or directory is removed from this repo, check whether a corresponding path still exists (or would exist) on a machine after `chezmoi apply`. If it should be destroyed there, add that destination-relative path to `.chezmoiremove`.

### Feature worktrees

Features are developed in workmux worktrees beside the source, at `../chezmoi__worktrees/<feature>` (set in `.workmux.yaml`). `workmux add <feature>` from the main checkout starts one from the last commit, so commit `master` first, or pass `-w` to carry uncommitted changes. chezmoi always reads one source, `chezmoi source-path` (the main checkout, on `master`), whatever the current directory: inside a worktree, a plain `chezmoi apply` applies `master`, and `chezmoi add` writes into `master`'s checkout. Inside a worktree (when `git rev-parse --show-toplevel` differs from `chezmoi source-path`), pass `--source "$(git rev-parse --show-toplevel)"` to every chezmoi command. The `chz*` shortcuts (`plugins/chezmoi`) do this for the read-only ones (`chzdi`, `chzapnv`) and refuse the others there. In Neovim (`features/chezmoi.lua`), a file saved in a worktree isn't auto-applied, and with Neovim's working directory in a worktree, `<leader>sz` lists and opens that worktree's files.

To try a feature, in this order of preference (`WT` is the worktree root):

- `chezmoi --source "$WT" diff`.
- Render into a scratch destination, then point the program at it: `PREVIEW=$(mktemp -d)`, then `chezmoi --source "$WT" --destination "$PREVIEW" --persistent-state "$PREVIEW/.state.boltdb" apply`. Programs: `XDG_CONFIG_HOME="$PREVIEW/.config" nvim`, `tmux -L feature -f "$PREVIEW/.config/tmux/tmux.conf"`, `kitty --config …`, `GIT_CONFIG_GLOBAL=…`.
- `chezmoi --source "$WT" apply <target>…` for only the targets being tested, for what only works in place (Hyprland, shell startup files).

Never apply a whole worktree: the next apply from `master` reverts its edits, and its new files stay in `$HOME` if the feature is abandoned.

To finish a feature: commit in the worktree (adding removed paths to `.chezmoiremove`), run `workmux merge --cleanup` (it rebases onto `master`, then removes the worktree, session and branch), run `chezmoi diff` and `chezmoi apply` from the main checkout, then push. To abandon one: `workmux remove <feature>` runs `dotfiles-worktree-check` (the `pre_remove` hook), which lists the files only the worktree manages that exist on disk, and stops the removal. Delete what shouldn't stay, or set `DOTFILES_CHECK_SKIP=1` to keep them. `chezmoi apply` from `master` restores the files the feature changed.

A feature's `run_once_` and `run_onchange_` scripts run when applied from its worktree. chezmoi records them by content hash in its shared state, so an abandoned or changed script can run again from `master`, and nothing undoes their effects outside `$HOME`. Templates never embed `.chezmoi.sourceDir` or a worktree path: the target would point into a worktree that gets deleted.

## Testing

Not every change is worth a test — cosmetic ones (comments, icons, wording) aren't. But changes to `tmux-attach`, `tmux-goto`, `tmux-session-cycle`, `dotfiles-worktree-check`, `android.plugin.zsh`, `chezmoi.plugin.zsh`, `gum.plugin.zsh`, `java.plugin.zsh`, `repos.plugin.zsh`, `workmux.plugin.zsh`, or the `machine`/`machine-layer`/`merge-data` partials (`tests/test-machine-data.sh`) should be tested: run the matching `tests/test-<name>.sh` after touching any of them, and extend it to cover new behavior (add a sibling `tests/test-<name>.sh` for a new script in the same spirit). These have all shipped real, silent regressions before — a genuinely empty picker icon, a bash-4-only builtin on a bash-3.2 system, a popup hijacking the wrong client, `status` being a read-only special variable in zsh that silently broke a function's error handling — so treat their logic like the production code it is. `tmux-workmux-open` (the bootstrap helper shared by `tmux-attach` and `workmux.plugin.zsh`) has no test file of its own: its logic is a strict subset of what `tests/test-tmux-attach.sh`'s "extracts the handle" case already exercises for real, and `tests/test-workmux-plugin.zsh` exercises the handoff to it via a fixture stub.

The bash scripts (`tests/test-tmux-*.sh`) source the script under test (each has a `BASH_SOURCE` guard so sourcing doesn't run its interactive/top-level entry point), redirect its `tmux` calls to a throwaway socket via a shadowed `tmux()` function so the real server is never touched, and assert against real tmux/git state. The zsh plugin tests (`tests/test-android-plugin.zsh`, `tests/test-chezmoi-plugin.zsh`, `tests/test-gum-plugin.zsh`, `tests/test-java-plugin.zsh`, `tests/test-repos-plugin.zsh`, `tests/test-workmux-plugin.zsh`) instead run the (unguarded, directly-sourced) script in a fresh `zsh -c` subshell per case, with `$HOME`/`$PATH` pointed at a throwaway fixture (for workmux, chezmoi and gum, a fake binary on `$PATH` that logs its arguments; for workmux also a fake `tmux-workmux-open` under the fixture `$HOME`), since these files are meant to be sourced directly with no interactive part to guard against. `tests/test-dotfiles-worktree-check.sh` runs the real `chezmoi` against a fixture `$HOME`, source and worktree inside one `mktemp` dir. Prefer exercising a real dependency over faking it when it's safe to (`test-workmux-plugin.zsh` uses the real `gum` binary — it's just a spinner around a command).

Match the runner to the file: `.zsh` files use zsh-only syntax (glob qualifiers, `${(q)...}`, `$+commands[...]`) that bash can't even parse, so their tests must run under real zsh — invoke them via their own `#!/usr/bin/env zsh` shebang or `zsh script.sh`, not `source`d into an ambient shell. This matters here specifically: this environment's own interactive shell is zsh, not bash, so a bash script sourced directly into it can silently misbehave (array substitutions in particular) instead of erroring — always exercise a script the same way its shebang says to, not however happens to be convenient.
