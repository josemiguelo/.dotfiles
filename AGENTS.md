# Agent instructions

## Git

Only run `git commit` or `git push` when the user explicitly asks to commit or push. Do not infer that from nearby work, “go”, or finishing a task.

If they ask to commit, follow their existing commit style (short lowercase imperative, why over what). If they ask to push, push the current branch. Do neither unless named in that turn.

## Layout

One repo for loadout and chezmoi. loadout's manifests are Kotlin (`*.loadout.kt`, all in package `repo`), compiled by `loadout compile` into `loadout.lock.json`, the only thing loadout reads; the repo root is the Gradle project that compiles them (`settings.gradle.kts`, `build.gradle.kts`, whose `loadout { sources(…) }` lists the manifest globs). `loadout.kt` declares the repo (`repo(…)`: state dir, configs dir, version floor), the `Data` schema (every per-machine setting with its default) and the built-in installers it uses; `machines/` holds the profiles and machines; `state/` is loadout's generated state. After editing any `.kt`, run `loadout compile` and commit the lock with the change (and the `configs/.chezmoidata/loadout.json` and `configs/.chezmoitemplates/loadout/` it writes): loadout refuses a lock older than its sources, and `.githooks/pre-commit` refuses the commit (enabled per clone with `git config core.hooksPath .githooks`; `bootstrap.sh` sets it). Compiling needs a JDK; reading the lock doesn't. chezmoi reads only `configs/` (`.chezmoiroot`): its special files (`.chezmoiignore`, `.chezmoiremove`, `.chezmoitemplates/`) live there, and nothing at the repo root is deployed.

Everything loadout knows about a tool that has a config sits beside that config: `.<tool>.loadout.kt` (its programs, scripts and their outdated sources) and `.loadout/` (their scripts), e.g. `configs/private_dot_config/zsh/.zsh.loadout.kt`. chezmoi never deploys dot entries that aren't its own special files, so neither reaches `$HOME`. Manifest file names are unique across the repo: they're all in one package, and two files of one name would compile to the same class. Paths in what a manifest file declares are relative to its folder, and its commands run there with `LOADOUT_REPO` set (moving a file with its scripts needs no edit); shared helpers live in `maintenance/lib/` (`"$LOADOUT_REPO/maintenance/lib/…"`). A tool whose config is a single file in a folder other tools share (e.g. `configs/private_dot_config/starship.toml`) is declared in `programs/` instead, since a manifest there would belong to no one tool. Config-less programs live in `programs/` (one-liners together, e.g. `programs/cli/cli.loadout.kt`; a tool with scripts or files of its own gets a folder) and config-less scripts in `maintenance/<platform>/<concern>/`, a folder per concern holding its manifest and scripts together, under the platform it runs on: `common/` (any OS: git, fonts, ssh keys), `linux/` (any distro: udev, systemd, T2 hardware, virtualization) and `omarchy/` (Omarchy's own setup). `maintenance/lib/` holds helpers every platform shares, and `omarchy/lib/` Omarchy's. `programs/brew/` holds the `brew`/`brew-cask` installers (replacing the built-ins so brew is reached by absolute path), `setup-brew`, and the `brew-tap`/`brew-tap-cask` installers (`tap(tap = "owner/tap")`, `tapCask(…)`: tapped and trusted by `brew-taps.sh`, then installed by full path); every brew installer `requires(setupBrew)`, so setup-brew precedes every brew install. `programs/dnf/` does the same for dnf (`setup-dnf`, `dnf-plugins-core` for COPRs). Anything else that needs brew by a custom command calls `sh "$LOADOUT_REPO/programs/brew/brew.sh" …`. Homebrew's prefix is decided only in `configs/private_dot_local/lib/brew-prefix.sh` (deployed to `~/.local/lib/`): anything that needs the prefix, or brew's `bin` on `PATH`, sources it and uses `$BREW_PREFIX`, never a hardcoded `/opt/homebrew` or `/home/linuxbrew`. Loadout's scripts source it from `$LOADOUT_REPO` (on a fresh machine they run before the dotfiles are applied), deployed files from `$HOME`.

Profiles and machines live in `machines/`: one file per machine, named by its hostname (`machines/t2-macbook-omarchy.loadout.kt`), one per profile in `machines/profiles/` (`omarchy.profile.loadout.kt`: `.profile` keeps the name apart from `programs/fedora.loadout.kt`), and `machines/shared.loadout.kt` for the lists several profiles use. They have two verbs: `install(programs…)`, inside `via(installer) { … }` for programs with several ways to install (one block per installer, holding every program the profile installs that way, single-variant ones included; outside a block go only programs with one variant and named variants, `program.variant(name = "linux")`) and `run(script, args…)` (one argument per line reads best; a script with variants is run as `script.variant(name = "arch")`). Shared lists (`everydayCli`, `shellScripts`) are plain `val`s; a profile still says which installer moves them. A profile holds what machines of a kind share (e.g. `omarchy`); a machine is a real host, named by its hostname, and `extends(…)` a list of profiles. `data { … }` sets its values. A machine overrides its profiles; two profiles of one list disagreeing is a compile error. A profile's long block can be a `MachineScope` function beside the scripts it configures, called from the profile (`omarchyBar()` in `maintenance/omarchy/shell/shell.loadout.kt`). `loadout compile` warns about what no machine uses (a profile, program, install variant, script or script variant); keep its output clean: use it, delete it, or say why it stays with `spare(reason = …)` where it's declared (the fedora profile, the macOS casks).

Templates branch on machine data, never on `.chezmoi.hostname`: `{{ if (includeTemplate "loadout/machine" . | fromJson).omarchy }}`. The `loadout/machine` partial picks this host's table from `.loadout` (`configs/.chezmoidata/loadout.json`); both are written by `loadout compile` and checked against the lock (loadout merges the defaults, the profiles and the machine), and a host the repo doesn't declare gets the defaults. Commit them with the lock, never edit them. A new setting is a new key in `loadout.kt`'s `Data` first, so it type-checks everywhere it's set. OS checks (`.chezmoi.os`) stay: the OS is a fact, not a setting.

## Chezmoi

Chezmoi does not delete destination files just because they left the source. Whenever a file or directory is removed from this repo, check whether a corresponding path still exists (or would exist) on a machine after `chezmoi apply`. If it should be destroyed there, add that destination-relative path to `.chezmoiremove`.

### Feature worktrees

Features are developed in workmux worktrees beside the source, at `../chezmoi__worktrees/<feature>` (set in `.workmux.yaml`). `workmux add <feature>` from the main checkout starts one from the last commit, so commit `master` first, or pass `-w` to carry uncommitted changes. chezmoi always reads one source, `chezmoi source-path` (the main checkout, on `master`), whatever the current directory: inside a worktree, a plain `chezmoi apply` applies `master`, and `chezmoi add` writes into `master`'s checkout. Inside a worktree (when `git rev-parse --show-toplevel` differs from `chezmoi source-path`), pass `--source "$(git rev-parse --show-toplevel)"` to every chezmoi command. The `chz*` shortcuts (`plugins/chezmoi`) do this for the read-only ones (`chzdi`, `chzapnv`) and refuse the others there. In Neovim (`features/chezmoi.lua`), a file saved in a worktree isn't auto-applied, and with Neovim's working directory in a worktree, `<leader>sz` lists and opens that worktree's files.

To try a feature, in this order of preference (`WT` is the worktree root):

- `chezmoi --source "$WT" diff`.
- `chztry <program> [args…]` from inside the worktree (`plugins/chezmoi`): it renders the whole worktree, minus scripts and externals, into `$XDG_RUNTIME_DIR/chztry/<feature>` (in memory; `$TMPDIR` without one), then runs the program with `XDG_CONFIG_HOME`, `ZDOTDIR` and `STARSHIP_CONFIG` pointing there and the preview's `~/.local/bin` first on `PATH`; `tmux` gets its own server (`-L chztry-<feature>`; `chztry tmux kill-server` before trying a changed `tmux.conf` again). E.g. `chztry nvim`, `chztry zsh`, `chztry tmux`, `chztry kitty`, `chztry yazi`. A program that reads its config from somewhere else needs its own variable added there, or rendering by hand: `chezmoi --source "$WT" --destination "$PREVIEW" --persistent-state "$PREVIEW.boltdb" apply --exclude scripts,externals`, then `GIT_CONFIG_GLOBAL=…` and the like.
- `chezmoi --source "$WT" apply <target>…` for only the targets being tested, for what only works in place (Hyprland, shell startup files).

Never apply a whole worktree: the next apply from `master` reverts its edits, and its new files stay in `$HOME` if the feature is abandoned.

To finish a feature: commit in the worktree (adding removed paths to `.chezmoiremove`), run `workmux merge --cleanup` (it rebases onto `master`, then removes the worktree, session and branch), run `chezmoi diff` and `chezmoi apply` from the main checkout, then push. To abandon one: `workmux remove <feature>` runs `dotfiles-worktree-check` (the `pre_remove` hook), which lists the files only the worktree manages that exist on disk, and stops the removal. Delete what shouldn't stay, or set `DOTFILES_CHECK_SKIP=1` to keep them. `chezmoi apply` from `master` restores the files the feature changed.

A feature's `run_once_` and `run_onchange_` scripts run when applied from its worktree. chezmoi records them by content hash in its shared state, so an abandoned or changed script can run again from `master`, and nothing undoes their effects outside `$HOME`. Templates never embed `.chezmoi.sourceDir` or a worktree path: the target would point into a worktree that gets deleted.

The same goes for a loadout script that writes its own path into a file outside the repo (an Omarchy hook, a command wrapper, as `omarchy-theme.sh` and `omarchy-scratchpad-opacity.sh` do): it takes that path from `main_checkout_path` (`maintenance/lib/main-checkout.sh`), which gives the main checkout's copy even when the script runs from a worktree. A worktree path would break silently once the feature merges and its worktree is removed. The trade-off: a hook installed while trying a feature runs `master`'s copy of its script, so a change to the script itself doesn't take effect through the hook until it merges (run the worktree's copy by hand to try it). A script new to the feature has no copy on `master` yet, so it writes its worktree path; loadout's `check` on `master` sees the path differ after the merge and installs again.

## Testing

Not every change is worth a test — cosmetic ones (comments, icons, wording) aren't. But changes to `tmux-attach`, `tmux-goto`, `tmux-session-cycle`, `tmux.plugin.zsh` (with `tmux-ensure-server` and `tmux-server-cwd`, `tests/test-tmux-plugin.zsh`), `dotfiles-worktree-check`, `android.plugin.zsh`, `chezmoi.plugin.zsh`, `gum.plugin.zsh`, `java.plugin.zsh`, `repos.plugin.zsh`, `workmux.plugin.zsh`, or the templates' use of loadout's `loadout/machine` partial (`tests/test-machine-data.sh`, after `loadout compile`) should be tested: run the matching `tests/test-<name>.sh` after touching any of them, and extend it to cover new behavior (add a sibling `tests/test-<name>.sh` for a new script in the same spirit). These have all shipped real, silent regressions before — a genuinely empty picker icon, a bash-4-only builtin on a bash-3.2 system, a popup hijacking the wrong client, `status` being a read-only special variable in zsh that silently broke a function's error handling — so treat their logic like the production code it is. `tmux-workmux-open` (the bootstrap helper shared by `tmux-attach` and `workmux.plugin.zsh`) has no test file of its own: its logic is a strict subset of what `tests/test-tmux-attach.sh`'s "extracts the handle" case already exercises for real, and `tests/test-workmux-plugin.zsh` exercises the handoff to it via a fixture stub.

The bash scripts (`tests/test-tmux-*.sh`) source the script under test (each has a `BASH_SOURCE` guard so sourcing doesn't run its interactive/top-level entry point), redirect its `tmux` calls to a throwaway socket via a shadowed `tmux()` function so the real server is never touched, and assert against real tmux/git state. The zsh plugin tests (`tests/test-android-plugin.zsh`, `tests/test-tmux-plugin.zsh` — which instead runs the real tmux on servers of its own via `TMUX_TMPDIR`, `tests/test-chezmoi-plugin.zsh`, `tests/test-gum-plugin.zsh`, `tests/test-java-plugin.zsh`, `tests/test-repos-plugin.zsh`, `tests/test-workmux-plugin.zsh`) instead run the (unguarded, directly-sourced) script in a fresh `zsh -c` subshell per case, with `$HOME`/`$PATH` pointed at a throwaway fixture (for workmux, chezmoi and gum, a fake binary on `$PATH` that logs its arguments; for workmux also a fake `tmux-workmux-open` under the fixture `$HOME`), since these files are meant to be sourced directly with no interactive part to guard against. `tests/test-dotfiles-worktree-check.sh` runs the real `chezmoi` against a fixture `$HOME`, source and worktree inside one `mktemp` dir. Prefer exercising a real dependency over faking it when it's safe to (`test-workmux-plugin.zsh` uses the real `gum` binary — it's just a spinner around a command).

Match the runner to the file: `.zsh` files use zsh-only syntax (glob qualifiers, `${(q)...}`, `$+commands[...]`) that bash can't even parse, so their tests must run under real zsh — invoke them via their own `#!/usr/bin/env zsh` shebang or `zsh script.sh`, not `source`d into an ambient shell. This matters here specifically: this environment's own interactive shell is zsh, not bash, so a bash script sourced directly into it can silently misbehave (array substitutions in particular) instead of erroring — always exercise a script the same way its shebang says to, not however happens to be convenient.
