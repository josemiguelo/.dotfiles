# t2-macbook-omarchy

A MacBookPro16,1 (16" 2019, T2, BCM4364B3 Wi-Fi and Bluetooth) running Omarchy on the stable channel, beside macOS: the macOS volume stays on the disk because the Wi-Fi firmware comes from it.

## The T2 stack

Omarchy's stock kernel, `linux-omarchy`, with [KaiT2en](https://github.com/kaiT2en/KaiT2en-Fedora)'s T2 drivers built by DKMS, not `linux-t2`. They come from the signed `[t2-arch-packages]` repo (`github.com/josemiguelo/t2-arch-packages`, key `077D8295CCF834D3F5EC25F70506B72C34EB162F`, its README has the test results):

- `t2bce-stack-dkms`: the internal keyboard and trackpad (in the initramfs, for the disk unlock prompt) and the audio transport. Touch Bar and keyboard backlight run on the kernel's own `hid-appletb-*` drivers on top of it.
- `t2-precision-trackpad-dkms`: the trackpad's multitouch and Force Touch. Stock kernels drive it as a plain mouse (no two-finger scroll, no tap to click; `linux-t2` patched `hid_magicmouse` for it). It loads first in the initramfs, so it holds the trackpad's interface before `hid-apple` can, which keeps the keyboard.
- `t2-wireless-dkms` (was `t2-bluetooth-dkms` until 2026-11-12): the kernel's `brcmfmac` (Wi-Fi) and `btbcm`, `hci_uart`, `hci_bcm4377` (Bluetooth) rebuilt from kernel.org 7.2.15 with KaiT2en's Apple Broadcom fixes 0001-0024. Wi-Fi: resume through a firmware reload (each wake re-probes the card: ~4.7 s to reconnect against 3.6 s, and no `brcmf` errors against 6), TX beamforming and ARP/ND offload off, host-side AP handshake, AWDL (inert until something uses it). DKMS keeps the stock `brcmutil` and `brcmfmac-wcc/-cyw/-bca`: built from the patched tree they're the same code, so `dkms status` says "Differences between built and installed modules", harmlessly. Bluetooth: stock `btbcm` drops most of this Mac's LE advertisements (`journalctl -k | grep 'unknown advertising packet type'`), so LE devices (the Keychron K15 Max, the MX Master 3) never show up or can't connect. It only builds for 7.2.x `-omarchy` kernels: on 7.3 the stock Wi-Fi and Bluetooth drivers come back, with that bug, until the package moves to 7.3 sources.
- `t2smc-dkms` (replaces `applesmc`, which can't reach the T2 SMC on a stock kernel): fans, charge limit (`charge_control_end_threshold` on `BAT0`), sensors, the EC clock. `t2sbs-dkms` (replaces `sbs`): the battery percentage relative to full charge, not to design capacity.
- `t2smp-dkms`, `t2thunderbolt-dkms` and the kernel arguments `pci=noaer pcie_ports=compat` (no `pm_async=off`): deep sleep wakes in about 1 s instead of 16. `pcie_ports=compat` costs native PCIe hotplug of Thunderbolt docks and eGPUs.
- `t2-fan-control` (replaces `t2fanrd`): its config is `/etc/t2-fancontrol/config.txt` with a system chill target of 80 °C. Upstream's 45 °C (the average of system and GPU sensors) pins this Mac's fans at full speed. The old `t2fanrd` curve throttled when it ramped late; watch for that under load with this curve.
- `t2-dsp` (with `bankstown-lv2`): KaiT2en's speaker and mic processing, the EQ, crossovers, compressor, limiters, crosstalk cancellation and virtual bass macOS applies to the 16" speakers, as PipeWire filter chains. A udev rule names the card `t2-16_1`; the default output is "Mac 16,1 native DSP Speakers" (the raw `HiFi__Speaker__sink` stays), the raw mic stays the default input (KaiT2en ranks its DSP mic lower). About 17% of one core while audio plays, nothing when idle; very low-latency apps (256-sample cycles) leave it little headroom. Pinned before KaiT2en's `6ddacd9`, which moved audio to its new driver.
- `t2-smc-control`: KaiT2en's SMC app and `t2-smc-gaugingd`. The battery stops at 85% (`args(script.t2-charge-limit, "85")`, the SMC's `CHLS`, which it keeps across reboots and in macOS); a permanent limit keeps the gauge from recalibrating, so the daemon lifts it (`battery_charge_limit_suspended`) for a full charge when the gauge's DOD0 is 3 days old or the last full charge 21, as macOS does. `script.t2-smc-gaugingd` keeps it running.
- `t2-dkms-guard`: aborts a `linux-omarchy` upgrade whose headers can't build these modules, so an update never drops the keyboard driver the disk unlock prompt needs. `sudo env T2_DKMS_GUARD_SKIP=1 pacman -Syu` overrides it.

Where it's built (`script.kait2en-dev` and `bare-repos` set all of it up, with the signing key from 1Password):

- **Packages**: `~/Repos/gh/josemiguelo/t2-arch-packages/all_worktrees/main`. `bin/kait2en-sync check` lists KaiT2en's commits per package since its pin (and the Fedora installer changes to review for `fix-t2.sh`), `apply` re-pins, builds, signs, tests and publishes, `kernel` builds every DKMS package against the newest `linux-omarchy-headers`. A daily user timer (`kait2en-sync.timer`) runs `notify`: a desktop notification for upstream updates, or for a new kernel the modules don't build against.
- **Omarchy**: the fork `josemiguelo/omarchy`, whose only branch (and default) is `t2-kait2en-stable`, in `~/Repos/gh/josemiguelo/omarchy/all_worktrees/t2-kait2en-stable` (`install/hardware/apple/fix-t2.sh`, `install/hardware/pacman.sh`; `upstream` is `omacom/omarchy`). It's the T2 commits on the commit Omarchy's stable package is built from (the `_commit` in omarchy-pkgs' `pkgbuilds/omarchy/PKGBUILD`), rebased onto the next one at each release. A personal project, nothing goes upstream, so there's no `quattro`-based branch (until 2026-11-12, `t2-kait2en` was one; the fork's other branches, copies of omacom's, were deleted then, listed in `~/.cache/omarchy-fork-deleted-branches-2026-11-12.txt`).
- **ISO**: the `t2-kait2en` branch of the fork `josemiguelo/omarchy-iso`, in `~/Repos/gh/josemiguelo/omarchy-iso/all_worktrees/t2-kait2en`, built there with `bin/omarchy-iso-make --keep-pkg-cache --no-boot-offer --local-source ~/Repos/gh/josemiguelo/omarchy/all_worktrees/t2-kait2en-stable ~/Repos/gh/omacom/omarchy-pkgs --stable` (stable channel, `release/*-local-stable.iso`), and tested on fake T2 hardware with `VFIO_USER_SERVER=~/Repos/gh/nutanix/libvfio-user/build/samples/gpio-pci-idio-16 OMARCHY_PATH=~/Repos/gh/josemiguelo/omarchy/all_worktrees/t2-kait2en-stable bin/omarchy-iso-test <iso> --fake-pci 106b:1802:088000` (QEMU and libvfio-user's build deps are this machine's `omarchy_iso_test_deps`). In a VM, `t2-wifi-firmware` (no macOS volume) and `systemd-modules-load` (`t2bce_vhci`: a fake device has no BCE) fail by design.

The ISO installs on stable. The first `omarchy update` replaces the branch's package (built as the recipe's `4.5.0-2`) with upstream's stable one. What `fix-t2.sh` set up stays, and loadout guards it (`t2-arch-packages-repo`, `t2-kernel-args`).

`loadouts/.etc/t2/` holds the rest: `local.kait2en` tracks the packages and `t2-arch-packages-repo` keeps the repo, its key and a `pre-refresh-pacman` hook (`omarchy refresh pacman` rewrites `pacman.conf` without the repo); the `t2-*` scripts fix the hardware below.

## Things to know

- **Its sshd lets in only named keys, from private networks**: `args(script.omarchy-sshd, …)` in `machines/profiles/t2-macbook.profile.loadout.hcl` lists the GitHub key titles it trusts (`github-ssh-key` titles a machine's key with the machine's name), and the firewall opens 22 to the private IPv4 ranges only. A new machine that should ssh in needs its name added there; any other key gets no shell, by design.
- **Its Wi-Fi firmware comes from the macOS volume**: `apple-bcm-firmware-fetcher` mounts it read-only with the APFS driver (`linux-apfs-rw-dkms`: `linux-t2` built APFS in, `linux-omarchy` doesn't) and copies the firmware to `/lib/firmware/brcm`. Its post-install run during an ISO install happens in the installer's chroot, which can't load the installed kernel's driver, so `fix-t2.sh`'s `t2-wifi-firmware.service` fetches at the installed system's boots until the fetcher has recorded its files, before networking starts. So whenever a request touches reinstalling Omarchy here or macOS's partition, warn the user first: erasing or reformatting the macOS volume leaves the next install without Wi-Fi. The fallback is the old `apple-bcm-firmware` package (14.0-1, gone from the repos, conflicting with the fetcher), a 1Password document (Personal vault, titled `apple-bcm-firmware-14.0-1-any.pkg.tar.zst`; Apple's firmware can't go into this public repo): `script.t2-bcm-firmware` uses the fetcher when a macOS volume is there and the package otherwise, restoring it from a verified copy in `/var/lib/t2-bcm-firmware/` or from 1Password over USB tethering or USB Ethernet. Without either, Wi-Fi is dead until the firmware comes from t2linux's `firmware.sh` (method 5, a macOS Recovery image downloaded from Apple). From Omarchy 4.5, `omarchy-update` also removes orphaned packages without asking (`omarchy-update-orphan-pkgs -y`, every `pacman -Qtdq`), so whichever package provides the firmware must stay explicitly installed: never let it become a dependency (`pacman -D --asdeps`).
- **Its Bluetooth degrades over many sleeps**: the BCM4364's Bluetooth runs with no firmware patch (`brcm/BCM.hcd` not found; nothing ships one for this chip, and it's the same on `linux-omarchy`). After days of suspends, Bluetooth audio stutters, drops, or stays connected but silent. Restarting bluetooth or rebooting doesn't fix it; a full shutdown does. `t2-bluetooth-dkms` carries KaiT2en's ACL priority and LE fixes; its Wi-Fi (`brcmfmac`) patches aren't ported yet.
- **Its clock lives in the EC**: `t2smc` reads and writes it (rtc1 on `linux-omarchy`), the legacy CMOS rtc (rtc0) only reads it. `script.t2-boot-clock` writes the time back at shutdown through `t2smc`, or the ACPI TAD where `t2smc` isn't loaded, picked by name.
- **Its T2 has a network link of its own**: `enp4s0f1u1` ("Apple T2 Controller", `05ac:8233`, MAC `ac:de:48:00:11:22`) is macOS's line to the T2 chip, a CDC NCM function on the BCE bus. No DHCP server answers on it, so `script.t2-ibridge-unmanaged` (and the fork's `fix-t2.sh`) keep NetworkManager off it with a udev rule. NetworkManager reads that tag only when a device appears, so a new rule takes effect at the next boot, or at once with `nmcli device set <iface> managed no`.

## Reinstalling

Keeps this hostname, so the machine and its state file stay `t2-macbook-omarchy`.

1. macOS: restore it if it's gone, and leave free space for Omarchy (Disk Utility, shrink the APFS container). The macOS volume must survive: it holds the Wi-Fi firmware.
2. Omarchy: check the stick holds a stable build before booting it: `grep -E '^omarchy(-settings)?(-dev)? ' /run/media/$USER/OMARCHY_*/arch/pkglist.x86_64.txt` lists `omarchy-settings`, not `omarchy-settings-dev` (a `-dev` there is an ISO built without `--stable`, which installs edge). Then boot it (Option at power-on; the live system boots `linux-t2` for the keyboard) and install **into the free space**, never over the whole disk.
3. First boot: `t2-wifi-firmware.service` fetches the Wi-Fi firmware before networking starts and brings the card up on it (`/usr/local/sbin/t2-wifi-reload`); `systemctl status t2-wifi-firmware` says how it went. Then `omarchy update`, and the bootstrap in the README with this machine's name; `script.t2-omarchy-channel` switches an install that came up on another channel back to stable.

What the 2026-11-10 reinstall showed (an ISO built before the fixes below):

- **The install stopped in "Configuring system"**: `fix-fkeys.sh` ran `omarchy-keyboard-toprow`, whose live write to `/sys/module/hid_apple/parameters/fnmode` fails in the installer's chroot (`/sys` is read-only there) and, under `set -e`, ended the phase. The fake-T2 VM test never loads `hid_apple`, so only the real Mac hits it. The fork (`t2-kait2en-stable`) leaves T2 Macs out of `fix-fkeys.sh` altogether, so the write never runs on them. (The deleted `t2-kait2en` also skipped the write wherever `/sys` isn't writable, a fix for other Macs not carried over.) An install stopped this way can be finished from the live ISO: open the LUKS root, mount `@`, `@home`, `@log`, `@pkg` and `/boot`, `arch-chroot` in and run the rest of the configuration by hand. The installer's last phase, the read-only `@factory` snapshot that `omarchy-system-factory-reset` restores, is then skipped unless taken by hand.
- **`omarchy-toprow.conf` overrides `t2-hid-apple-keyboard`**: an install from an ISO before that fix leaves `/etc/modprobe.d/omarchy-toprow.conf` with `fnmode=1`, which sorts after `hid_apple.conf` and wins, so the script stays pending after every boot and Fn+arrows don't work. Its other lines are for ASUS drivers: delete the file, then `loadout run t2-hid-apple-keyboard` and reboot.
- **`t2-wifi-firmware.service` reported a failure** although Wi-Fi came up after a reboot: its `modprobe -r brcmfmac` ran into `brcmfmac_wcc`, which holds it.

What the 2026-11-11 reinstall showed:

- **It came up on edge**: the stick held an ISO built that morning, before omarchy-iso's `--stable` existed, so it installed `omarchy-dev` and the edge repo. Nothing said so until `pacman -Q`; `script.t2-omarchy-channel` now catches it, and step 2 checks the stick.
- **No Wi-Fi on the first boot, fine after a reboot**: `brcmfmac` probes at coldplug, before `t2-wifi-firmware` has copied the firmware, and fails (`brcmfmac4364b3-pcie.bin failed with error -2`). Its pending firmware request holds the module for ~4 s more, then unbinds the card (with a `cancel_work_sync` warning in `brcmf_pcie_remove`). The fetcher's own reload runs inside that window, its `modprobe -r brcmfmac` fails, and it ignores the error. The fork's unit now runs `t2-wifi-reload` after the fetcher: it retries removing the driver (and its holders) until the request lets go, loads it again, and fails the unit only if the card still has no interface. `fix-t2.sh` can't name the driver (`test/shell.d/brcmfmac-supplicant-test.sh` keeps `brcmfmac` to one leaf), so the script finds it from the card's PCI class and modalias.
