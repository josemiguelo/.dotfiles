# Local LLM for Obsidian

The T2 MacBooks (`machines/profiles/t2-macbook.profile.loadout.ts`) run a local LLM that the vault's Copilot plugin uses, with nothing leaving the machine: llama.cpp's `llama-server` serving Qwen 3.6 35B-A3B, Copilot in `~/Obsidian/vaults/jm`, and Miyo for search by meaning. Everything listens on `127.0.0.1` only.

## The pieces

- **`llama-server`** (`program.llama-cpp` + `program.ggml-vulkan`, `script.llama-server`): the only piece that writes text. A user service (`llama-server.service`) on `:8080` with an OpenAI-compatible API (`/v1`), model alias `qwen3.6-35b-a3b`. The machine's options for it are its environment and flags, so the tuning below lives in the profile, commented. Its GPU is named, not numbered (`--vulkan-gpu Radeon`): Vulkan numbers the GPUs by which one drives the display, which the T2's boot GPU decides, and at login the user service starts about a second before the Radeon is up. A fixed `GGML_VK_VISIBLE_DEVICES=1` therefore found no device 1 at every boot and llama.cpp quietly ran on the CPU (prompts ~30 tok/s, answers ~3 tok/s, the fans at full speed). The unit's `ExecStartPre` (`llama-server.ts gpu-env`) waits up to 90 s for a Vulkan device with that name and writes its number to `%t/llama-server/gpu.env`, the unit's `EnvironmentFile`; `script.llama-server`'s check also wants the running server to hold memory on a GPU, and no more than 256 MiB of other programs' memory there, so a CPU fallback or a crowded GPU shows as pending (`loadout bun loadouts/llama-cpp/.loadout/llama-server.ts gpu-state` shows who's on it). Crowded is how it crashed: Superwhisper's offline models (ggml, which picks the discrete GPU) reserved ~2.9 GB of the Radeon, and with llama-server's ~3.2 GB beside them its GPU jobs overran amdgpu's timeout; the driver reset the compute ring and llama.cpp aborted on `vk::DeviceLostError`, again at every restart. `script.superwhisper-gpu` now pins Superwhisper's workers to the iGPU with a `superwhisper.service` drop-in that sets Mesa's device-select layer (`MESA_VK_DEVICE_SELECT=8086:3e9b`, forced: they see no other GPU).
- **The tray switch** ([llama-toggle](https://github.com/thesilentbear/llama-toggle), added by the T2 profile's `omarchyBarFn({ plugins, widgets })`): a pill in the bar's tray that starts and stops `llama-server.service` (`systemctl --user`; its `models` setting, in `omarchy-bar/settings/dev.thesilentbear.llama-toggle.json`, names only that unit, or it would list `llama-warmup` too). Off frees the Radeon and ~21 GB of RAM, for a game say; on runs the GPU lookup and the warm-up, as every start does. `script.llama-server`'s check accepts it stopped, so loadout doesn't turn it back on. Nothing else does either: the unit has no `[Install]`, so after a login or a reboot it stays off until this switch (or `systemctl --user start llama-server`) starts it.
- **The model** (`script.llm-model`, later): `unsloth/Qwen3.6-35B-A3B-GGUF`, `UD-Q4_K_M` (21 GB) in `~/.local/share/llm-models`, pinned to a commit of that repo and by SHA-256. A Mixture-of-Experts model: 256 experts, 8 at work per token (~3B of 35B parameters), which is what makes a CPU-bound laptop usable. Qwen publishes no GGUF of its own; unsloth's is the most used, and its dynamic quant keeps the important layers at higher precision.
- **The warm-up** (`llama-warmup.service`, written by `script.llama-server`, runs `llama-server.ts warmup`): after every server start, replays Agent Chat's setup prompt (~12K tokens: OpenCode's instructions, ~30 tool definitions, the skills list) so the prompt cache holds it. The first Agent message after a start then answers in ~7 s instead of ~90 s. The server logs every prompt into `$XDG_RUNTIME_DIR/llama-server/prompts` (tmpfs: conversations never reach the disk, and logging out or shutting down wipes them); when it stops (a restart, a logout, a shutdown), `llama-server.ts refresh` (its `ExecStopPost`) keeps the setup part, up to the first user turn, of the newest Agent Chat prompt there in `~/.local/share/llm-models/warmup/` and deletes the logs. When Copilot, OpenCode or the skills change that prompt, the next first message is slow once, and from the next server start the warm-up replays the new one. Its only varying line, `Today's date:`, is rewritten at replay. The server won't start without its verified model (`ConditionPathExists`, and `script.llama-server` refuses to install), so a failed download can't become a restart loop.
- **Copilot** (`script.obsidian-copilot`, after `script.obsidian-vault`): the chat UI, a community plugin in the vault. Installed from its pinned release (4.0.20, its files checked against SHA-256s) only when missing, so Obsidian's updater moves it afterwards. The script keeps in its `data.json`: the `llama.cpp` provider and the model (ids fixed in the script, so chats' model references stay valid) with the server's context size, which Copilot passes on to OpenCode (it assumes 200K otherwise), that model first in Quick Chat's and OpenCode's lists and as Agent Chat's explicit default, and Miyo's search on, for Copilot and the agents, at 8 results. The default matters: without one, Copilot hands OpenCode the first enabled model, and OpenCode adds cloud models of its own (OpenCode Zen's free ones) to that list, so a new machine could send notes to the cloud. They stay in the picker; a chat only uses one when picked. The script waits for Obsidian to be quit before it writes. **Quick Chat** sends a message and the attached notes (`[[…]]`, `@`) straight to `llama-server`: small prompts, the everyday mode. **Agent Chat** hands the conversation to OpenCode.
- **OpenCode**: the agent loop behind Agent Chat. Copilot downloads and runs its own copy (`~/.obsidian-copilot/opencode/<version>/`, config in `OPENCODE_CONFIG_CONTENT`), apart from Omarchy's mise `opencode`. It sends Qwen the setup prompt and runs the tools Qwen asks for (read and edit notes, shell, Miyo's search) until there's an answer. It shares `~/.config/opencode` and `~/.local/share/opencode` with the mise one: it loads `workmux-status` (whose server side is a no-op) and would put every skill in `~/.claude/skills`, `~/.agents/skills` and the vault's `.opencode/skills` into its prompt (a third of it), but for `script.obsidian-opencode`.
- **Agent Chat's context** (`script.obsidian-opencode`): `<vault>/.opencode/opencode.json`, a project config, so only the OpenCode Copilot runs in the vault reads it. OpenCode compacts when the chat reaches the window less `compaction.buffer` (default 16,000 tokens: at 16.8K of 32K, measured against a stub server; the model's output limit doesn't matter) and keeps `compaction.keep` tokens of it (default 15,000): 5,000 and 6,000 move it to ~27.7K. Its `permissions` deny every skill but the vault's own three; a skill added for Claude Code no longer changes the setup prompt.
- **Agent Chat's grep** (`script.obsidian-rgignore`): Copilot tells the agent to grep alongside every Miyo search, and OpenCode's grep is ripgrep with `--hidden`, so a search returned mostly Copilot's `main.js` and its chat logs (~90% of ~12K characters). `<vault>/.rgignore` skips `.obsidian`, `.copilot` and `copilot/copilot-conversations` (measured with a stub server: 12.3K to 1.6K and 14.8K to 1.3K characters); a grep that names one of them still searches it. Only ripgrep reads that file, so a plain `rg` in the vault skips them too.
- **Miyo** (`program.miyo` + `script.miyo-launcher`, later): a free desktop app by Copilot's makers (miyo.md) that Copilot V4 needs for search by meaning; Copilot itself only searches exact text. It watches the vault, splits notes into chunks, turns each into an embedding (numbers for its meaning) with its own llama.cpp on `:8750` (`jina-embeddings-v5-text-nano`, 223 MB), keeps them in Qdrant (`:6333`), and answers searches on `:8742` (hybrid: embeddings plus keywords, 4-15 ms). It never writes answers: Agent Chat's `obsidian-copilot_miyo_search` tool hands its chunks to Qwen. Its index lives in `~/.config/Miyo`. Installed from the latest release (SHA-512 checked; `fuse2` for the AppImage) as `~/.local/share/miyo/Miyo.AppImage`, linked as `~/.local/bin/miyo-app`. It updates itself, and the name has no version on purpose: its updater replaces such a file in place, but deletes a versioned one for the new version's name, which would leave the link and the launcher pointing at nothing. Autostarted at login, since Copilot's search needs it running. `miyo` is its CLI (`miyo search`, `miyo parse`, `miyo mcp`), which it links into `~/.miyo/bin` at every launch, from inside its mounted AppImage: it works only while Miyo runs (as does everything it asks). On PATH from `~/.zshenv`, on the machines whose data says `miyo: true`, as Miyo's own marked block: whenever its CLI link is gone (after every reboot, the mount it points into being new) Miyo reinstalls it and rewrites that block, but leaves an identical one alone, so chezmoi carries it verbatim. The login shell reads `~/.zshenv`, so the whole session, and every agent's `zsh -c`, has the folder on PATH. Its own `startOnLogin` uses Electron's login items, which do nothing on Linux: the autostart entry is the launcher script's alone. Both entries run `~/.local/share/miyo/launch`, a wrapper that finds the iGPU's Vulkan number by name (`--vulkan-gpu Intel`) at each launch and execs Miyo. The launcher also sets Miyo's `openDashboardOnStartup` to false: closing Miyo's window quits it, which at login left Copilot without search.

What runs where: the Radeon (4 GB) holds Qwen's attention and shared weights and the KV cache (~3.2 GB); RAM holds the 256 experts (~21 GB), computed by the CPU, and the prompt cache (up to 8 GB); the Intel iGPU drives the display, Miyo's embeddings and Superwhisper's dictation models (`miyoLauncher("--vulkan-gpu Intel")`: by default its llama.cpp spreads over both GPUs and takes ~0.7 GB of the Radeon).

## A new machine

`machine new` installs and configures all of it; the model, the server and Miyo come in its later phase. Its core phase stops twice for Obsidian, as it does for 1Password, and goes on by itself (each waits up to `OBSIDIAN_WAIT` seconds, default 900):

1. **`obsidian-vault`** opens Obsidian and waits for the vault: log in under Settings → Sync and connect the remote vault to `~/Obsidian/vaults/jm`. Obsidian keeps its account and Sync state where no script can read them, so it waits for what a finished sync leaves on disk: the vault in `~/.config/obsidian/obsidian.json`, its `.obsidian` and a note, then `OBSIDIAN_QUIET` seconds (default 30) without a file changing, after which it leaves a marker in `~/.local/state/loadout/` (a re-run after a timeout waits for the settle again).
2. **`obsidian-copilot`** then asks to quit Obsidian (it rewrites plugin settings while it runs), installs and configures Copilot, and setup goes on.

What's left by hand, afterwards (the server stays off until switched on: its tray switch, for OpenCode's Agent Chat and Quick Chat):

1. **Obsidian**: Settings → Community plugins → "Turn on community plugins" (kept outside the vault).
2. **Agent Chat**: Copilot downloads OpenCode the first time Agent Chat is picked (Settings → Copilot → Basic → Agents → OpenCode → Configure → Managed by Copilot, if it asks).
3. **Miyo**, launched once: "Get started", skip "AI chats" and "Any folder", no Relay. Then Obsidian → Settings → Copilot → Miyo → Connect → "Register & connect" (Miyo running), which registers the vault in Miyo's own index.
4. **The warm-up** learns Agent Chat's setup prompt from the first Agent chat: that one is slow (~90 s); the server keeps it when it stops, and from then on the first message of a chat takes ~7 s.

## Why it's tuned this way

Measured on this Mac (16" 2019, i9-9980HK, 64 GB DDR4, Radeon Pro 5500M 4 GB, RDNA1: no ROCm, so Vulkan):

- **Qwen 3.6 35B-A3B over Gemma 4 26B-A4B**: ~2.5× faster prompt reading, ~1.6× faster generation, and a more complete answer over vault notes. A dense 27B model would run at ~2 tok/s.
- **llama.cpp over Ollama**: Ollama can only put whole layers on the GPU (~2 GB of 22), so the GPU barely helped (prompt ~50 tok/s, generation ~10). llama.cpp's `-ngl 99 --n-cpu-moe 41` puts every layer's non-expert weights on the GPU and keeps all experts in RAM; with `-ub 2048 -b 2048` the GPU does prompt math in big batches: **~150-175 tok/s prompt reading, ~13 tok/s generation**. `-ub 4096` read 201 tok/s in llama-bench but leaves less VRAM; more expert layers on the GPU (`--n-cpu-moe 36`) added little.
- **`GGML_OP_OFFLOAD_MIN_BATCH=1024`**: for every batch of 32+ tokens llama.cpp copies the experts to the GPU, a loss for small prompts (an 86-token follow-up took 8 s). With 1024: 64 tokens 16 → 75 tok/s, 256 tokens 40 → 110, 4096 unchanged.
- **`-c 32768`**: 16K overflowed after three Agent Chat turns (the setup prompt alone is ~12K); Copilot assumed a 200K window and didn't warn, so `script.obsidian-copilot` now tells it the real one. VRAM: 16K 2.9 GB, 32K 3.2 GB, 64K 4.0 GB (full).
- **Thinking off** (`enable_thinking: false`): with it on, both models spent a 2048-token budget (~5 min) thinking on a planning question without answering.

Timings to expect: Quick Chat starts answering in a few seconds plus ~1 s per 150 tokens of attached notes; Agent Chat ~7 s on a new chat (OpenCode's per-message title request is most of it), a search turn ~40 s (search, reading ~2K tokens of results, writing).

## Things to know

- Booted on the Radeon (the T2's boot GPU reset, as on 2026-11-20; `t2-boot-gpu` sets it back for the next boot), the Radeon drives the display, and Hyprland, the shell and Superwhisper's dictation models fill its 4 GB: llama-server finds its GPU by name but has no room. Reboot onto the iGPU.
- The Radeon reads ~0 VRAM when idle: amdgpu suspends it after 5 s and moves its memory to RAM, and the next request wakes it in under 2 s, at full speed.
- Arch's Obsidian runs as `electron … /usr/lib/obsidian/app.asar`: no process is named `obsidian`, and `pgrep -f obsidian/app.asar` also matches any shell that mentions it; `#obsidian` reads `/proc` for an electron with that argument.
- Answers from Miyo's chunks only see excerpts: the agent once called a note "cut off" that wasn't. Ask it to open the note, or link it (`[[…]]`), for the whole file.
- Prompt logs pile up in `$XDG_RUNTIME_DIR` (RAM) while the server runs, ~50-100 KB per Agent Chat request; the server clears them each time it stops.
- Re-tuning: `loadout bun loadouts/llama-cpp/.loadout/bench.ts <model file> [vulkan device] [llama-bench args…]` stops the server, runs llama-bench and starts it again. `journalctl --user -u llama-server` shows each request's prompt and generation speed; `journalctl --user -u llama-warmup` the last warm-up.
