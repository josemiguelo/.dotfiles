# Where things live

`loadout.ts` declares the repo (`repo({ … })`: state dir, the tool folders, version floor, the data schema from `machines/data.ts`) after including every manifest (`include("loadouts/*/*.loadout.ts", "machines/**/*.loadout.ts")`). Manifests import the SDK as `"loadout"` (a module inside loadout, typed by `node_modules/@types/loadout`, which compile writes, out of git) and each other by relative path: every declaration is an exported, typed reference. `machines/` holds the machines, their profiles and state (`docs/machines.md`). `.githooks/pre-commit` refuses a commit whose lock is older than its sources (enabled per clone with `git config core.hooksPath .githooks`; `bootstrap.sh` sets it).

## A tool, one folder

Everything about a tool is one folder, `loadouts/<tool>/` (`dotfiles: { tools: "loadouts/*", … }` in `loadout.ts`):

- `<tool>.loadout.ts`: its programs, scripts and their outdated sources. A tool with several has several, by what they're about (`loadouts/omarchy/omarchy-shell.loadout.ts`, `omarchy-webapps.loadout.ts`…).
- `.loadout/`: the scripts and files they run.
- `home/`: its dotfiles, chezmoi source rooted at `$HOME`, with chezmoi's names (`home/private_dot_config/kitty/kitty.conf.tmpl` → `~/.config/kitty/kitty.conf`), wherever in `$HOME` they land: zsh's are `~/.zshenv` and `~/.config/zsh/`, tmux's include its scripts in `~/.local/bin`.
- `root/`: what it puts outside `$HOME`, chezmoi source rooted at `/` (`loadouts/keychron/root/etc/udev/rules.d/…`), applied as root; a folder already there keeps its mode, a symlinked one stays a symlink.
- `home/.chezmoiignore` and `home/.chezmoiremove`: what's off a machine, and what left the tool and should leave the machines.

Each part is there only when the tool has it: a one-liner is a folder holding one manifest (`loadouts/ripgrep/`), a tool with dotfiles and nothing to install is a folder holding `home/` (`loadouts/tmuxinator/`). The folder is named after the tool, and that name is its unit in `loadout machine status` for what `root/` puts in `/` (`/keychron`). A folder in a tool that isn't `home/` or `root/` is a compile warning: a misspelt one would deploy nothing. A declaration is used before it's declared only across files: within one, declare what a list uses first.

chezmoi doesn't read the tool folders: loadout builds its sources from them, `.chezmoi-home/` (every `home/`, which `.chezmoiroot` names) and `.chezmoi-root/` (every `root/`), symlinks to the tools' files, kept current by every loadout command and ignored by git. Edit the files in the tool folders; for chezmoi's own commands that write the source, use `loadout chezmoi` (`re-add`, `add --tool <tool>`, `chattr`, `forget`), which carries what chezmoi wrote over to the tool's folder.

## Outside `$HOME`

What a tool does outside `$HOME` stays with the tool: a file is in its `root/`, a step that needs a check, a reload or a question is a script in its `.loadout/` (virtualization's services in `loadouts/libvirt/`, Omarchy's sshd in `loadouts/ssh/` beside the client side). What belongs to no app is a tool named after its concern: `loadouts/t2/`, `loadouts/keychron/`.

## Scripts and helpers

Paths in a manifest are relative to its folder, and its commands run there with `LOADOUT_REPO` set, so moving a file with its scripts needs no edit. Helpers several apps share live in `lib/`; one app's live in its own `.loadout/lib/` (Omarchy's in `loadouts/omarchy/.loadout/lib/`, Hyprland's in `loadouts/hypr/.loadout/lib/`, each used by the other); scripts import both by name (the `#` imports below), never by a relative path.

## Bun scripts

A loadout script is a TypeScript module the manifest imports, `module: () => import("./.loadout/x.ts")`: it exports `check` and `install`, and the `Options` they take, if any, are what a machine calls the script with; loadout runs it with its Bun, no `#!` line. One that takes options has rules, `rules: () => import("./.loadout/x.rules.ts")`: that file exports `Options` and `validate`, which returns what's wrong with them, for what their type can't say (`() => undefined` when the type says it all). Compile calls it with every machine's options and loadout before `check` and `install`, so the module never does; compile runs the file, so nothing else goes in it. One that systemd or a hook also runs keeps those modes under `if (import.meta.main)`. Ask one with `loadout script check <script>` (`--options '<json>'` for other values). `check`, `install`, `listOutdated`, `newerVersion` and `update` are exported where they're declared, under those names. An `updates` module exports `listOutdated` and `update(item)` (a program's: `newerVersion` and `update`). A file a manifest runs as a command (`runFile()`) has a `#!/usr/bin/env bun` line and calls `runStep(step)` from `"loadout/script"` (loadout's script SDK, inside loadout like the manifests', typed by the same `node_modules/@types/loadout`) with a named function; Bun Shell's ``$`…` `` runs commands, one argument per `${value}`. A script prints on stderr: `console.warn` for progress and why a check says no (Bun prints `console.error` in red, so it's only for a failure), and `tell` for what the user has to do. Shared modules are imported by name, never by `../` path: `"loadout/script"` (loadout's: the protocols, `env`, outdated rows, `clonesBehind`, the Bun Shell helpers), `#brew` (`lib/brew.ts`: brew by its path, the prefix from brew-prefix.sh), `#user` (`lib/user.ts`: a command the user answers on the terminal, waiting for what they do elsewhere, and `tell`, which prints what the user has to do in yellow), `#bare-repo` (`lib/bare-repo.ts`: bare clones with their default branch's worktree, for bare-repos and skills-repo), `#ssh` (`loadouts/ssh/.loadout/lib/`: the agent a script's ssh reaches, and its key in it), `#hypr` (`loadouts/hypr/.loadout/lib/`: Hyprland's config and the running Hyprland), `#omarchy` and `#webapp` (`loadouts/omarchy/.loadout/lib/`: the Omarchy shell, bar widgets, plugins, menu entries and command overrides; Omarchy web apps), `#nvim` (`loadouts/nvim/.loadout/lib/`: headless Neovim for the lazy plugins and Mason), `#tmux` (`loadouts/tmux/.loadout/lib/`: the plugins tmux.conf declares and their clones), `#onepassword` (`loadouts/1password/.loadout/lib/`: the CLI connected, unlocked in the open, and secrets read), `#antidote` (`loadouts/zsh/.loadout/lib/`: antidote and the bundles .zplugins declares), `#android-sdk` (`loadouts/android-sdk/.loadout/lib/`: the SDK directory Android Studio manages, the pins, and Studio's sdkmanager), `#llama-cpp` (`loadouts/llama-cpp/.loadout/lib/`: where the local LLM's model, units and warm-up live) and `#obsidian` (`loadouts/obsidian/.loadout/lib/`: the vault argument, the running app, and waiting on the user for it), from `package.json`'s `imports` (a new one is a line there). loadout is the Bun they run with: it's built with one (`loadout bun --version`) and puts itself first on PATH as `bun` for every command it runs, from a new machine's first step, so a file a program or installer names (`module`, an installer's `runFile()`) can be TypeScript too. mise's bun (`loadouts/mise/home/private_dot_config/mise/config.toml`) is the shells' and the editor's; `.githooks/pre-commit` refuses a commit of `loadout.ts` or mise's config where mise's pin isn't loadout's bun. `bun install` at the repo root gives the editor Bun's types, and the pre-commit hook the TypeScript it type-checks with (`node_modules`, not committed); the scripts never need it. What stays `sh`: `bootstrap.sh`, which installs loadout itself, and what zsh sources (`brew-prefix.sh`, read by `#brew`).

## Homebrew and flatpak

Every brew installer needs setup-brew (`withBrew.needs(setupBrew)`), and setup-brew `addsToPath: { brew: … }`, so brew's `bin` is on `PATH` for every command probed through it on a fresh machine; flatpak (`loadouts/flatpak/flatpak.loadout.ts`) works the same way. Anything else that needs brew calls `brew(…)` from `#brew` in a script, or `.loadout/brew.ts …` in a manifest (`runFile()`).

Homebrew's prefix is decided only in `loadouts/homebrew/home/private_dot_local/lib/brew-prefix.sh`: source it and use `$BREW_PREFIX` (a script: `brewPrefix()` from `#brew`, which sources it), never a hardcoded `/opt/homebrew` or `/home/linuxbrew` (loadout's scripts source it from `$LOADOUT_REPO`, since they run before the dotfiles are applied; deployed files from `$HOME`). The one exception is setup-brew's `addsToPath: { brew: … }`, which loadout reads without a shell: change it with `brew-prefix.sh`.
