# Where things live

`loadout.ts` declares the repo (`repo({ … })`: state dir, configs dir, version floor, the scripts' bun, the data schema from `machines/data.ts`) after including every manifest (`include("loadouts/**/*.loadout.ts", "machines/**/*.loadout.ts")`). Manifests import the SDK as `"loadout"` (`tsconfig.json`'s `paths` to `loadout.sdk.ts`, which compile writes) and each other by relative path: every declaration is an exported, typed reference. `machines/` holds the machines, their profiles and state (`docs/machines.md`). chezmoi reads only `loadouts/`: its special files (`.chezmoiignore`, `.chezmoiremove`, `.chezmoitemplates/`) live there. `.githooks/pre-commit` refuses a commit whose lock is older than its sources (enabled per clone with `git config core.hooksPath .githooks`; `bootstrap.sh` sets it).

## A thing lives where it lands

Everything loadout knows about a tool that lands in `$HOME` sits in chezmoi's source at that spot: `.<tool>.loadout.ts` (its programs, scripts and their outdated sources) and `.loadout/` (their scripts and files).

- A tool with dotfiles has them beside it: `loadouts/private_dot_config/zsh/.zsh.loadout.ts`, `loadouts/private_dot_config/.starship.loadout.ts` beside `starship.toml`.
- A tool without any gets the same spot behind a dot. A one-liner is a file in its destination's parent (`loadouts/private_dot_config/.ripgrep.loadout.ts`: `~/.config` unless the tool's home is elsewhere, like `loadouts/.ssh/` or `loadouts/private_dot_local/share/.fonts/`); one with scripts or files of its own is a dot-folder named after it (`loadouts/private_dot_config/.gcloud/.gcloud.loadout.ts` + `.loadout/`). When it gains a config, drop the dot (`git mv .gcloud gcloud`), as ngrok did (`private_ngrok/`: private, since its config holds a token).
- Never a plain folder holding only a manifest: chezmoi creates it, empty, in `$HOME`. Dot entries that aren't chezmoi's own never reach `$HOME`.
- `include`'s globs match dot files and folders, so a manifest is found wherever it sits under `loadouts/` or `machines/`, as long as its name ends in `.loadout.ts`. A declaration is used before it's declared only across files: within one, declare what a list uses first.
- Omarchy's own setup of `$HOME` is `loadouts/private_dot_config/.omarchy/` (its shell and bar, overrides, scratchpad, web apps, the `omarchy-<app>` scripts) and `.hypr/` (Hyprland).

## Outside `$HOME`

An app whose work happens outside `$HOME` still lives with the app: virtualization in `.libvirt/`, Omarchy's sshd in `loadouts/.ssh/` beside the client side, Homebrew in `.homebrew/`. What belongs to no app is in `loadouts/.etc/<concern>/`, the same shape (`.<concern>.loadout.ts` + `.loadout/`): `.etc/t2/`, `.etc/keychron/`. So a dot-folder at the root of `loadouts/` is always a place in `$HOME` (`.ssh/`).

## Scripts and helpers

Paths in a manifest are relative to its folder, and its commands run there with `LOADOUT_REPO` set, so moving a file with its scripts needs no edit. Helpers several apps share live in `lib/` (`"$LOADOUT_REPO/lib/…"`); one app's live in its own `.loadout/` (Omarchy's in `.omarchy/.loadout/lib/`, used by `.hypr/` too). A script that also runs outside loadout (an Omarchy hook) reaches them relative to itself (`$HERE/../../../../lib/…`): nothing sets `LOADOUT_REPO` there.

## Bun scripts

A loadout script is TypeScript run by Bun (`#!/usr/bin/env bun`, a `.ts` file; loadout runs a file with its `#!` interpreter): `main(check, install)` from `"loadout/script"` (loadout's script SDK, `loadout.script.ts`, which compile writes beside the manifests' SDK) is the `check` / install protocol (`run(step)` for a manifest's `file` with its check inline); the functions given to `main` and `run` are named and declared before the call, never written in it (`await main(ready, install)`, `await run(outdated)`), and Bun Shell's ``$`…` `` runs commands, one argument per `${value}`. Shared modules are imported by name, never by `../` path: `"loadout/script"` (loadout's: the protocols, `env`, outdated rows, `clonesBehind`, the Bun Shell helpers), `#brew` (`lib/brew.ts`: brew by its path, the prefix from brew-prefix.sh), `#bare-repo` (`lib/bare-repo.ts`: bare clones with their default branch's worktree, for bare-repos and skills-repo), `#ssh` (`.ssh/.loadout/lib/`: the agent a script's ssh reaches, and its key in it), `#hypr`, `#omarchy` and `#webapp` (`.omarchy/.loadout/lib/`: Hyprland's config and the running Hyprland; the Omarchy shell, bar widgets, plugins, menu entries and command overrides; Omarchy web apps), `#nvim` (`nvim/.loadout/lib/`: headless Neovim for the lazy plugins and Mason), `#tmux` (`tmux/.loadout/lib/`: the plugins tmux.conf declares and their clones), `#onepassword` (`.1password/.loadout/lib/`: the CLI connected, unlocked in the open, and secrets read) and `#antidote` (`zsh/.loadout/lib/`: antidote and the bundles .zplugins declares), from `package.json`'s `imports` (a new one is a line there). loadout is the Bun they run with: it's built with one (`loadout bun --version`) and puts itself first on PATH as `bun` for every command it runs, from a new machine's first step, so a file a program or installer names (`installedBy`, `managedBy`, an installer's `runScript()`) can be TypeScript too. mise's bun (`mise/config.toml`) is the shells' and the editor's; `.githooks/pre-commit` refuses a commit of `loadout.ts` or mise's config where mise's pin isn't loadout's bun. `bun install` at the repo root gives the editor Bun's types (`node_modules`, not committed); the scripts never need it. What stays `sh`: `bootstrap.sh`, which installs loadout itself, and what zsh sources (`brew-prefix.sh`, read by `#brew`).

## Homebrew and flatpak

Every brew installer `requires` setup-brew, and setup-brew `provides: { brew: { at: … } }`, so brew's `bin` is on `PATH` for every command probed through it on a fresh machine; flatpak (`loadouts/private_dot_local/share/.flatpak.loadout.ts`) works the same way. Anything else that needs brew calls `brew(…)` from `#brew` in a script, or `.loadout/brew.ts …` in a manifest (`runScript()`).

Homebrew's prefix is decided only in `loadouts/private_dot_local/lib/brew-prefix.sh`: source it and use `$BREW_PREFIX` (a script: `brewPrefix()` from `#brew`, which sources it), never a hardcoded `/opt/homebrew` or `/home/linuxbrew` (loadout's scripts source it from `$LOADOUT_REPO`, since they run before the dotfiles are applied; deployed files from `$HOME`). The one exception is setup-brew's `provides: { brew: { at: … } }`, which loadout reads without a shell: change it with `brew-prefix.sh`.
